Interactive Warehouses: Zero-Copy vs Interactive Tables

Benchmark study on SFSENORTHAMERICA-RGOLDIN_AWS1 · 18 fixed-concurrency runs plus 4 concurrency ramps · TPCH SF100 orders, 150M rows · September 2026

Headline. Querying a standard table directly on an interactive warehouse performs the same as a dedicated interactive table — the 3.4 % gap we measured is indistinguishable from noise. What actually matters is clustering: a clustered standard table delivered +19 % throughput and 30 % lower median latency than the same table unclustered.

Practical read: adopt zero-copy freely, and spend your effort on the clustering key instead of on converting tables.

Background

On 14 September 2026, zero-copy support for all table formats in interactive warehouses reached general availability. Interactive warehouses can now query standard, dynamic, Iceberg, and hybrid tables directly, with no copy into a dedicated interactive table. The documentation goes further than "supported" and calls standard tables the "best default, same performance as Interactive tables."

This study tests that claim, and answers three practical questions that came up while setting it up.

1. Do tables need to be attached to the warehouse?

No — attachment is optional. ALTER WAREHOUSE … ADD TABLES is a cache-warming hint; unattached tables are still queryable and cached on demand. Attaching is nonetheless recommended, because it lets Snowflake populate the cache proactively.

Tooling gap worth knowing. The Snowsight dialog is titled "Attach interactive tables" and its object picker filters to interactive tables only, so a standard table appears impossible to attach. That is a UI limitation, not a server one — the SQL works:

ALTER WAREHOUSE my_iwh ADD TABLES (db.schema.my_standard_table);

The picker predates the GA and hasn't caught up. Use SQL.

2. Will automatic clustering fix a badly laid-out table on its own?

No. Automatic Clustering — both Classic and the newer Optima Clustering — only operates on tables that already have a user-defined clustering key. There is no auto-discovery. An unclustered table stays unclustered indefinitely.

The other Optima features that do work without a clustering key — Optima Indexing, Optima Metadata, Optima Planning — are documented as available on Snowflake generation 2 standard warehouses and Adaptive Warehouses. Interactive warehouses are not in that list. On an interactive warehouse there is no automatic rescue for poor data layout.

3. Does a running warehouse mean a warm warehouse?

No, and this one bit us. Two caches warm independently of warehouse state: the data cache (per table, per micro-partition) and the compile/metadata cache (per query shape). Both were measured cold on a warehouse that had been running for eight hours — see single-query measurements.

CREATE TABLE … CLUSTER BY (O_ORDERDATE, O_CUSTKEY) AS SELECT * FROM … ORDER BY O_ORDERDATE, O_CUSTKEY;

Exploratory phase: concurrency ramps

Four FIND_MAX_CONCURRENCY ramps were run first to locate each configuration's saturation point. These are useful for finding the knee but, as shown below, unreliable as a head-to-head comparison.

Throughput vs concurrency. All configurations are identical below ~20 workers because nothing is contended. The unclustered table's knee arrives around 26 workers; clustered and interactive keep scaling to ~36–41. Two interactive-table runs are shown to illustrate run-to-run variability.

p95 latency vs concurrency. Curves are tightly bunched at low concurrency and diverge only as each configuration saturates.

Why we abandoned ramp mode for the comparison. The ramp stops when p95 exceeds a percentage of the step-1 baseline — and step 1 is a single cold worker. Two runs of the identical interactive-table configuration stopped at 41 and 66 workers respectively, purely because one baseline was a cold 112 ms and the other a clean 71 ms.

A worse baseline buys a run more headroom, which inverts the metric's meaning. Peak QPS from a ramp is trustworthy; maximum concurrency is not comparable across runs. Everything that follows uses fixed concurrency.

The ordering artifact

Median QPS per matrix. In Matrix 1 the interactive table led by 7.8 %; after rotating the run order in Matrix 2, the clustered standard table led by 3.1 %. The verdict reversed sign — the strongest evidence that the original advantage was cache-warmth ordering, not table type.

What went wrong in Matrix 1. The clustered table declined monotonically across its three trials — 489.8 → 466.8 → 432.9 QPS. Its best number came from the very first run of the night, before the other two tables had been driven under load, so it had the warehouse data cache largely to itself. The interactive table, already warm for days, was the only configuration that did not decline.

The within-configuration spread (13.1 %) was larger than the 7.8 % gap being attributed to table type. That alone should stop a conclusion.

Metric selection matters. Reporting p95 from a saturated run would have shown "no difference between any configuration" — including between clustered and unclustered, which differ by 19 % in throughput. Use QPS and p50 for capacity comparisons; drop to roughly 20 connections if you want to compare latency. The server-side view in the next section recovers the signal that end-to-end p95 hides.

Server-side execution time

Every number above is end-to-end: the elapsed time the driver observed, which includes client-side scheduling, network round trip, Snowflake query compilation, and finally the query execution itself. That is the right metric for "what will my application feel", but it buries the engine's contribution under transport and compile cost.

FlakeBench enriches each recorded query with the values Snowflake itself reports, so the execution phase can be isolated. The figures below come from QUERY_EXECUTIONS.SF_EXECUTION_MS, which is QUERY_HISTORY.EXECUTION_TIME — pure server-side execution, with no client, network, or compilation time in it. They are pooled over 6,006,727 enriched, non-warmup, successful query rows across all 18 runs (99.99 % enrichment coverage).

Why the three worker rows matter. Each run is executed by three SPCS workers, and QUERY_EXECUTIONS is keyed by the per-worker TEST_ID, not the aggregate one. The per-query rows are reached by joining the aggregate run (CONCURRENT_CONNECTIONS = 45) to its three worker rows (CONCURRENT_CONNECTIONS = 15) on RUN_ID. Filtering QUERY_EXECUTIONS on the aggregate TEST_ID returns nothing.

The headline result. On an interactive warehouse, a well-clustered table — interactive or standard — executes this point lookup in 7 ms at the median and under 15 ms at p99. The same query against the unclustered copy takes 47 ms. The engine difference is nearly seven-fold; the application only sees 1.4× because transport and compilation dominate what it measures.

Where the rest of the time goes

Median latency decomposition. For the fast configurations, actual query execution is the smallest component: 7 ms of execution behind 27 ms of compilation and roughly 37 ms of client and network time. Each segment is its own pooled median, so the segments do not sum exactly to the end-to-end median.

Server execution as a share of end-to-end median latency. On the tuned configurations less than a tenth of what the application waits for is the database executing the query.

This decomposition explains the earlier p95 result. At 45 connections, end-to-end p95 was pinned at 147–153 ms for all three configurations, which looked like "table layout does not matter". It actually meant the queueing and transport terms were large enough to swamp a real 7-vs-77 ms difference in the engine. Two further consequences are worth noting:

  • Client overhead scales with throughput, not with table quality. The client-plus-network median was ~37 ms for the fast configurations but only ~10 ms for the unclustered one, because the unclustered runs pushed 20 % less traffic and so queued less on the client side. This works against the good configurations in end-to-end numbers, understating their true advantage.
  • Compilation is the dominant Snowflake cost here. 27 ms of compile against 7 ms of execution. For a workload of this shape, prepared or parameterised statements would cut more latency than any further table tuning.

Stability and the ordering artifact

Server p95 execution time per run, in matrix order. Unlike the QPS series, these show no monotonic drift across the matrix — the clustered configuration sits flat at 10 ms after its first run, so the cache-warmth effect that reversed the throughput verdict does not appear in server execution times.

Because the transport and queueing noise is stripped out, server-side percentiles separate interactive tables from clustered standard tables where end-to-end metrics could not. Across the six trials per configuration:

  • p95: 9.2 ms (interactive) vs 10.3 ms (clustered standard) — Welch t ≈ 3.13, p ≈ 0.017.
  • p99: 13.3 ms vs 15.2 ms — Welch t ≈ 4.04, p ≈ 0.005.
  • p50: 7 ms in every interactive run; 7 ms in five of six clustered runs. Indistinguishable.

Read this carefully. SF_EXECUTION_MS has integer-millisecond resolution, so a 1–2 ms tail difference sits close to the measurement floor. The result is statistically detectable and consistent in sign — interactive tables have a slightly tighter tail — but it is a ~1 ms effect on a ~72 ms end-to-end request. It does not change the practical conclusion that the two are interchangeable for this workload; it only changes it from "no measurable difference" to "a measurable difference too small to act on".

Learnings

About the feature

  1. Zero-copy is real and costs nothing measurable. A clustered standard table on an interactive warehouse matched a dedicated interactive table. There is no throughput or latency penalty for skipping the conversion.
  2. Clustering is the lever, not table type. +19 % throughput and −30 % p50 from clustering alone. Every clustered run beat every unclustered run.
  3. Nothing clusters itself. Automatic and Optima Clustering require a user-defined key. The Optima features that work without one are not available on interactive warehouses.
  4. Attachment is optional but worthwhile, and must be done in SQL — the Snowsight picker still filters to interactive tables only.
  5. A running warehouse is not a warm warehouse. Per-query-shape compile cache and per-table data cache both warm independently of warehouse uptime.

About benchmarking

  1. Rotate run order, always. Fixed ordering produced a clean, plausible, and wrong result. Rotation reversed it.
  2. Watch for monotonic drift within a configuration — it is the tell-tale sign of an ordering artifact.
  3. Know the noise floor before believing a difference. Ours was ~6 % CV even with 720-second runs and warm caches. Treat sub-10 % differences as unresolved.
  4. Match the metric to the load point. p95 is meaningless as a discriminator from a saturated run.
  5. Avoid baseline-relative stop conditions. A ramp that stops at "p95 > N % of a cold baseline" is not comparable across runs.
  6. Hold data layout constant when comparing table types — otherwise you are measuring layout and calling it type.

Existing table, not clusteredAdd a clustering key matching your WHERE predicates. This is where the gain is — not in converting to an interactive table.

Caveats

  • Single query shape. One selective two-predicate lookup on one table. Results may differ for joins, aggregations, or wider scans.
  • Single warehouse size. Medium, single cluster. Not a scaling study.
  • Small working set. The table is ~4 GB and fits comfortably in a Medium cache. A working set that exceeds cache would likely widen the clustering gap further.
  • One account, one region. No cross-region or cross-cloud comparison.
  • Saturated operating point. Conclusions about p95 apply to 45 connections on this warehouse; a lower load point would separate latency differently.
  • Equivalence is bounded, not proven. The study shows any interactive-vs-clustered difference is below ~10 %; it does not prove the difference is exactly zero.
